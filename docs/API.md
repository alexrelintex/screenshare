# API reference

The signaling service does three things: mint room ids, report who is in a room,
and relay handshake messages between two peers. It never sees a video frame.

Base URL below is written as `https://sig.example.com`. Interactive docs are
served at `/docs` (OpenAPI schema at `/openapi.json`).

📮 **[Postman collection](screenshare.postman_collection.json)** — import it and
run "Mint a room" first; it stores the room id so the other requests need
nothing pasted by hand. Point `baseUrl` at `http://127.0.0.1:8000` to work
against a local `make up`. It also runs headless:
`npx newman run docs/screenshare.postman_collection.json`.

| | |
|---|---|
| [`POST /rooms`](#post-rooms) | Mint a room, get links and embed code |
| [`GET /rooms/{room_id}`](#get-roomsroom_id) | Who is in a room right now |
| [`GET /healthz`](#get-healthz) | Liveness, and how many rooms are open |
| [`WS /ws/{room_id}`](#ws-wsroom_id) | The signaling channel itself |

## Room ids

A room id is the name two peers agree on. It is generated by
`secrets.token_urlsafe(9)` — 12 URL-safe characters, about 72 bits.

**The room id is the only secret.** There is no authentication on a room: anyone
who knows an id and reaches the service can join it. That single fact drives
everything else on this page.

| Property | Value |
|---|---|
| Format | `[A-Za-z0-9_-]{12}` |
| Entropy | ~72 bits |
| Case sensitive | Yes |
| Lifetime | Created by the first peer to connect, destroyed when the last leaves |
| Capacity | 2 peers. A third is rejected with `room-full` |

### A minted id is not a reservation

`POST /rooms` allocates nothing server-side. Rooms exist only while peers are
connected, so a fresh id names a room that does not exist yet. Two consequences:

- **Unused ids cost nothing.** No cleanup job, no expiry, no storage. This is
  what makes an unauthenticated endpoint affordable.
- **Nothing holds the room for you.** If an id leaks before your customer opens
  their link, whoever has it can take the second seat, and your customer then
  gets `room-full`. Send links over a channel you trust.

### Ids do not survive a restart

Rooms live in one process's memory. A deploy, a crash, or a free-tier instance
sleeping drops every room. Peers already connected keep streaming — media is
peer-to-peer and does not need the server once negotiated — but they cannot
renegotiate, and a peer who reloads will not find the other. Treat ids as valid
for the length of one call, not as records to store against a CRM object.

Two replicas do not share rooms; see [Limits](../README.md#limits--read-before-deploying).

## POST /rooms

Mint a room and return a matched pair of links plus paste-ready embed snippets.
No request body, no authentication.

```bash
curl -X POST https://sig.example.com/rooms
```

**`201 Created`**

```json
{
  "room": "L15lGVkwSZ3y",
  "signaling": "https://sig.example.com",
  "host": {
    "url": "https://app.example.com/demo/index.html?room=L15lGVkwSZ3y&mode=host&signaling=https%3A%2F%2Fsig.example.com",
    "embed": "<script src=\"https://app.example.com/dist/screenshare.js\" async></script>\n<screen-share room=\"L15lGVkwSZ3y\" signaling=\"https://sig.example.com\" mode=\"host\"></screen-share>"
  },
  "viewer": {
    "url": "https://app.example.com/demo/index.html?room=L15lGVkwSZ3y&mode=viewer&signaling=https%3A%2F%2Fsig.example.com",
    "embed": "…same, with mode=\"viewer\""
  }
}
```

| Field | Meaning |
|---|---|
| `room` | The generated id |
| `signaling` | The URL both ends must point at |
| `host.url` / `viewer.url` | Openable page links, with `signaling` carried in the query string so they work regardless of how the page was deployed |
| `host.embed` / `viewer.embed` | HTML to paste into a page you control |

Both roles name the same room — that is the point of the pair. Give one end to
each participant; whichever is *sharing* takes `host`.

### Configuration

Links are built from two environment variables:

| Variable | Meaning | Unset |
|---|---|---|
| `APP_BASE_URL` | Where `demo/index.html` and `dist/screenshare.js` are served | Falls back to the request URL |
| `SIGNALING_PUBLIC_URL` | This service's own public URL | Falls back to the request URL |

The fallback is fine locally and unreliable behind a proxy, which reports
whatever it forwarded. Set both in any real deployment — otherwise the links
point back at the signaling service, which serves no page.

Neither base is accepted from the caller. An endpoint that let a client name its
own base would mint links that look like yours and point anywhere else.

## GET /rooms/{room_id}

Who is in a room right now. Useful for showing "waiting for customer…" against a
CRM record, or for deciding whether to re-send a link.

```bash
curl https://sig.example.com/rooms/L15lGVkwSZ3y
```

**`200 OK`**

```json
{ "room": "L15lGVkwSZ3y", "peers": 1, "capacity": 2, "occupied": true, "full": false }
```

| Field | Meaning |
|---|---|
| `peers` | Connected peers, 0–2 |
| `capacity` | Always 2 — this is 1:1 by design |
| `occupied` | `peers > 0` |
| `full` | `peers >= capacity`; a further join is rejected |

### An unknown room returns 200, not 404

A room nobody has joined reads as `peers: 0`. This is deliberate: a link that has
been sent but not yet opened is the *normal* case, and reporting it as an error
would mean treating the expected path as a failure. Absent and empty are the
same state.

So `occupied: false` does not distinguish "never opened" from "call finished"
from "id was never valid". If you need those apart, record when you minted the id
on your side.

### Polling

There is no push notification for occupancy. Poll no faster than every few
seconds; nothing here changes quickly, and each request wakes a sleeping
free-tier instance. Do not poll to keep an instance warm — a room that drops
because the instance slept is not saved by knowing it dropped.

Probing for occupied rooms is not a practical attack at 72 bits of entropy, but
this endpoint does confirm an id when handed one. It reveals a count, never a
peer identity or any session content.

## GET /healthz

```bash
curl https://sig.example.com/healthz
```

```json
{ "status": "ok", "rooms": 3 }
```

`rooms` counts rooms with at least one peer — the load the process is carrying,
not a total ever created. Used as the container health check and by Render.

## WS /ws/{room_id}

The signaling channel. The widget speaks this for you; you only need it if you
are writing your own client.

Connect and the server replies with `welcome`, then announces the other peer's
arrival and departure:

```json
{"type": "welcome",     "peerId": "…", "peers": ["…"]}
{"type": "peer-joined", "peerId": "…"}
{"type": "peer-left",   "peerId": "…"}
{"type": "error",       "code": "room-full"}
```

You may send exactly three types — `offer`, `answer`, `ice` — which are relayed
verbatim to the other peer with a `from` field added. Anything else is rejected
rather than forwarded, so a room cannot be used as a general message bus.

| Error code | Cause |
|---|---|
| `room-full` | A third peer tried to join. The socket is then closed with 1008 |
| `frame-too-large` | Frame over 64 KB |
| `bad-json` | Not valid JSON |
| `unsupported-type` | Not one of `offer` / `answer` / `ice` |

Unknown message types from the server are ignored by the client rather than
treated as errors, so adding one does not break already-embedded widgets.

## Embedding

### 1. Get a room

```js
const res = await fetch("https://sig.example.com/rooms", { method: "POST" });
const session = await res.json();
```

CORS allows `POST` from any origin, so a browser can call this directly. If you
put authentication in front of the endpoint, call it from your backend instead —
that keeps the credential off the page.

### 2. Put one end on your page

Paste `session.viewer.embed` (or build it yourself):

```html
<script src="https://app.example.com/dist/screenshare.js" async></script>
<screen-share
  room="L15lGVkwSZ3y"
  signaling="https://sig.example.com"
  mode="viewer"></screen-share>
```

The element renders in an open shadow root, so your CSS cannot reach in and its
styles cannot leak out. It registers one custom element name and sets no
`window` properties. Loading the script twice is a no-op.

### 3. Send the other end to the other participant

`session.host.url` — a plain link, nothing to install.

### 4. React to what happens

All events bubble and cross the shadow boundary:

```js
const el = document.querySelector("screen-share");
el.addEventListener("ss-state",  (e) => console.log(e.detail.state));
el.addEventListener("ss-error",  (e) => console.warn(e.detail.error));
el.addEventListener("ss-tap",    (e) => console.log("pointed at", e.detail));
```

See the [attribute and event tables](../README.md#attributes) for the full set.

### Which end goes in the CRM

Put the **viewer** in your CRM and send the **host** link to whoever is sharing
their screen — usually the customer. That ordering is not arbitrary; the next
section is why.

## ⚠️ iframe behaviour

Most CRMs render third-party content in an iframe. Three things break there, and
two of them fail silently enough to look like your bug.

### Screen capture is blocked unless the parent grants it

`getDisplayMedia` is gated by the `display-capture` Permissions Policy. Inside an
iframe it throws `NotAllowedError` — indistinguishable, from inside, from a user
who cancelled the picker — **unless the parent page opts in**:

```html
<iframe src="https://app.example.com/…" allow="display-capture"></iframe>
```

**You cannot grant this to yourself.** It must come from the page that contains
the iframe. If you do not control the CRM's iframe markup, `mode="host"` cannot
work there, and no amount of code on your side changes that.

This is the whole reason for putting the viewer in the CRM: **viewer mode needs
no permissions.** It receives a stream and reports pointer positions, so it works
in any iframe, sandboxed or not.

### Fullscreen needs its own grant

The `fullscreen` attribute and the Full screen button call `requestFullscreen()`,
which an iframe may not do unless the parent allows it:

```html
<iframe src="…" allow="display-capture; fullscreen"></iframe>
```

Without it the widget falls back to a fixed-position overlay that fills the
iframe rather than the screen — it will look like fullscreen "did nothing" if the
iframe is small. Nothing throws.

### A sandboxed iframe needs scripts

```html
<iframe src="…" sandbox="allow-scripts allow-same-origin"></iframe>
```

`allow-scripts` alone leaves the frame in an opaque origin, where WebRTC and
`getDisplayMedia` are unavailable. Both attributes or neither.

### Everything requires a secure context

`getDisplayMedia` and `RTCPeerConnection` need HTTPS (or `localhost`). Plain HTTP
on a LAN address will not work, and an HTTPS page cannot open a `ws://` signaling
socket — the browser blocks it as mixed content. Serve both over TLS.

### Checklist for a CRM embed

| Requirement | Viewer | Host |
|---|---|---|
| HTTPS on both page and signaling | Required | Required |
| `allow="display-capture"` from parent | — | **Required** |
| `allow="fullscreen"` from parent | For real fullscreen | For real fullscreen |
| `sandbox="allow-scripts allow-same-origin"` if sandboxed | Required | Required |

If you control neither the iframe nor its `allow` attribute: embed the viewer,
and send the host link out as a URL to open in a normal tab.

## Limits

Read [Limits](../README.md#limits--read-before-deploying) before deploying. The
short version: no TURN, so peers behind symmetric NAT will fail to connect; no
authentication, so room ids are the only secret; single process, so rooms do not
survive a restart or scale past one replica.
